## Lições Aprendidas

### Django

#### Model Design
**Aprendizado 1: Custom User Model**
```python
# ❌ Problema inicial: Usar User padrão do Django
from django.contrib.auth.models import User

# ✅ Solução: Custom User desde o início
class Usuario(AbstractUser):
    cpf = models.CharField(max_length=14, unique=True)
    setor = models.CharField(max_length=100)
```
**Por quê:** Depois de ter dados no banco, migrar para custom user é muito difícil.

---

**Aprendizado 2: ForeignKey vs CharField**
```python
# ❌ Problema: Guardar nome como string
fototipo = models.CharField(max_length=20)

# ✅ Solução: Usar ForeignKey
fototipo = models.ForeignKey(Fototipo, on_delete=models.PROTECT)
```
**Por quê:** Ao acessar `interessado.fototipo.upper()`, dá erro porque não é string. O correto é `interessado.fototipo.nome`.

---

**Aprendizado 3: Índices de Performance**
```python
# ❌ Sem índice: Busca lenta em 10.000+ registros
cpf = models.CharField(max_length=14, unique=True)

# ✅ Com índice: Busca rápida
cpf = models.CharField(max_length=14, unique=True, db_index=True)
```
**Quando usar:** Campos que você filtra/busca frequentemente (CPF, email, datas).

#### Queries

**Aprendizado 4: Problema N+1**
```python
# ❌ Problema: 1000 inscrições = 1000+ queries
inscricoes = Inscricao.objects.all()
for inscricao in inscricoes:
    print(inscricao.evento.nome)  # Query para cada uma!

# ✅ Solução: select_related
inscricoes = Inscricao.objects.select_related('evento').all()
for inscricao in inscricoes:
    print(inscricao.evento.nome)  # Sem queries extras!
```
**Regra de ouro:** Sempre usar `select_related` para ForeignKey e OneToOne.

---

**Aprendizado 5: Prefetch para ManyToMany**
```python
# ❌ Problema: Muitas queries para relacionamentos múltiplos
classificacoes = Classificacao.objects.all()
for c in classificacoes:
    for criterio in c.inscricao.inscricaocriterioatendido_set.all():
        print(criterio.nome)

# ✅ Solução: prefetch_related
classificacoes = Classificacao.objects.prefetch_related(
    'inscricao__inscricaocriterioatendido_set__criterio'
).all()
```
**Quando usar:** Relacionamentos ManyToMany e reverse ForeignKey.

### Arquitetura

**Aprendizado 8: Service Layer**
```python
# ❌ Problema: Lógica complexa na view
def classificar_view(request, evento_id):
    # 200 linhas de lógica aqui
    pass

# ✅ Solução: Service Layer
class ClassificadorService:
    @staticmethod
    def classificar_evento(evento):
        # Toda lógica aqui
        pass

def classificar_view(request, evento_id):
    ClassificadorService.classificar_evento(evento)
```
**Por quê:** 
- Reutilização (admin, view, command)
- Testabilidade
- Organização

**Aprendizado 9: Transactions**

```python
from django.db import transaction

@transaction.atomic
def classificar_evento(evento):
    # Se der erro, TUDO é revertido

    for inscricao in inscricoes:
        criar_classificacao(inscricao)
```
**Quando usar:** Operações que devem ser "tudo ou nada".

### Erros Comuns Resolvidos

#### Erro 1: AttributeError em ForeignKey
**Erro:**
```python
AttributeError: 'Fototipo' object has no attribute 'upper'
```

**Causa:**
```python
if interessado.fototipo.upper() in racas_cotistas:  # ❌
```

**Solução:**
```python
if interessado.fototipo.nome in racas_cotistas:  # ✅
```

**Lição:** ForeignKey retorna objeto, não string. Acesse o campo do objeto.

---

#### Erro 2: Campo inexistente
**Erro:**
```python
AttributeError: 'Interessado' object has no attribute 'tipo_deficiencia'
```

**Causa:** Tentando acessar campo que não existe no model.

**Solução:** Verificar quais campos existem:
```python
class Interessado(models.Model):
    pcd_fisica = models.BooleanField(default=False)
    pcd_visual = models.BooleanField(default=False)
    # ... etc
```

**Lição:** Sempre consultar o model antes de acessar campos.

---

#### Erro 3: Classificação com 0 pontos
**Problema:** Todos candidatos com 0 pontos mesmo tendo critérios.

**Causa:** 
```python
if criterio.tipo == 'PONTUACAO':  # ❌ Campo 'tipo' não existe
```

**Solução:**
```python
if criterio.tipo_criterio == 'PONTUACAO':  # ✅ Campo correto
```

**Lição:** Verificar nome exato dos campos no banco.

### Decisões de Design

#### Decisão 1: Dois Sistemas de Autenticação
**Contexto:** Staff precisa de username, interessados usam CPF.

**Solução:** Custom authentication backend
```python
class InteressadoBackend:
    def authenticate(self, request, cpf=None, password=None):
        # Busca por CPF ao invés de username
        pass
```

**Alternativas consideradas:**
- Usar username para todos (❌ CPF é mais natural para público)
- Apenas um tipo de usuário (❌ Permissões muito diferentes)

---

#### Decisão 2: Tipo de Critério (Pontuação vs Ordenação)
**Contexto:** Alguns critérios somam pontos, outros apenas ordenam.

**Solução:** Campo `tipo_criterio` no Criterio
```python
class Criterio(models.Model):
    tipo_criterio = models.CharField(
        choices=[
            ('PONTUACAO', 'Pontuação'),
            ('ORDENACAO', 'Ordenação')
        ]
    )
```

**Alternativas consideradas:**
- Apenas pontuação (❌ Não permite ordem de inscrição)
- Models separados (❌ Duplicação de código)

---

#### Decisão 3: Prioridade em EventoCriterio
**Contexto:** Ordem de aplicação dos critérios deve ser flexível.

**Solução:** Campo `prioridade` que define ordem
```python
class EventoCriterio(models.Model):
    prioridade = models.IntegerField(default=1)
```

**Alternativas consideradas:**
- Ordem fixa (❌ Sem flexibilidade)
- Ordenação alfabética (❌ Não faz sentido)

### Conceitos Importantes

#### Conceito 1: Classificação Híbrida
Sistema combina dois tipos de critérios:

**PONTUACAO:** Soma pontos
- PCD: +10 pontos
- NIS: +5 pontos
- Total: 15 pontos

**ORDENACAO:** Define ordem de desempate
- IDADE_CRESCENTE: mais jovem primeiro
- ORDEM_INSCRICAO: cronológica

**Resultado:**
1. Ordena por pontos (maior primeiro)
2. Critérios de ORDENACAO por prioridade
3. Data de inscrição como último desempate

---

#### Conceito 2: Vagas Reservadas
**Vagas Totais:** 100
**Vagas Reservadas:** 20% (20 vagas)

**Processamento:**
1. Classifica todos candidatos
2. Separa reserva (20 primeiros que atendem critério)
3. Restante (80 vagas) para classificação geral

**Vantagem:** Respeita cotas sem complicação.

---

#### Conceito 3: Lista de Espera
**Classificado:** Dentro do número de vagas
**Lista de Espera:** Fora das vagas mas classificado

**Status:**
- `classificado=True, lista_espera=False` → Aprovado
- `classificado=False, lista_espera=True` → Lista de espera
- `classificado=False, lista_espera=False` → Não classificado

### Analogias Úteis

#### Analogia 1: Select_Related
```
Sem select_related:
Você vai na padaria buscar pão.
Aí lembra que precisa de leite.
Volta no mercado.
Aí lembra que precisa de café.
Volta de novo.
(Muitas viagens = muitas queries)

Com select_related:
Você faz uma lista antes de sair.
Busca tudo de uma vez.
(Uma viagem = uma query)
```

---

#### Analogia 2: Service Layer
```
Restaurante sem chef (Views fazendo tudo):
Garçom precisa saber cozinhar.
Cada garçom faz do seu jeito.
Difícil de treinar novos garçons.
Inconsistência nos pratos.

Restaurante com chef (Service Layer):
Chef especializado em receitas complexas.
Garçom só anota pedido e entrega.
Receitas centralizadas.
Qualidade consistente.
```

---

#### Analogia 3: Fixtures
```
Fixtures são como "save game":

Sem fixtures:
Toda vez que criar novo banco, precisa cadastrar:
- Status manualmente
- Critérios manualmente
- Etc.

Com fixtures:
python manage.py loaddata criterios
(Tudo pronto em segundos)
```

### Glossário de Termos

**Model:** Representação de uma tabela no banco de dados
**View:** Função que processa uma requisição e retorna resposta
**Template:** Arquivo HTML com placeholders para dados
**Admin:** Interface administrativa do Django
**ORM:** Object-Relational Mapping (trabalha com objetos, não SQL)
**Migration:** Arquivo que aplica mudanças no banco de dados
**Fixture:** Arquivo JSON com dados iniciais
**QuerySet:** Lista de objetos de um model
**ForeignKey:** Relacionamento "um para muitos"
**ManyToMany:** Relacionamento "muitos para muitos"
**Select_related:** Otimização para ForeignKey/OneToOne
**Prefetch_related:** Otimização para ManyToMany
**Transaction:** Grupo de operações "tudo ou nada"
**Service Layer:** Camada para lógica de negócio complexa
**Custom User:** Model de usuário personalizado
**Abstract Base Class:** Model base sem tabela própria
**Inline:** Edição de models relacionados na mesma tela

### Perguntas Frequentes (FAQ)

**P: Por que usar PostgreSQL e não SQLite?**
R: SQLite é ótimo para desenvolvimento, mas PostgreSQL é mais robusto para produção com múltiplos usuários simultâneos.

**P: Por que separar apps (eventos, interessados, selecao)?**
R: Modularização. Cada app tem uma responsabilidade clara, facilitando manutenção e testes.

**P: Por que criar ClassificadorService?**
R: Lógica complexa não deve ficar em views ou admin. Service centraliza e permite reutilização.

**P: Quando usar select_related vs prefetch_related?**
R: select_related para ForeignKey/OneToOne (faz JOIN), prefetch_related para ManyToMany (faz queries separadas).

**P: Por que usar fixtures?**
R: Dados iniciais (status, critérios) precisam estar sempre disponíveis. Fixtures tornam isso reproduzível.

**P: Como debugar queries lentas?**
R: Usar django-debug-toolbar para ver quantas queries são executadas e onde.
